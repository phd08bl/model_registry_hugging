# 3. Target control loop

Refactor the top-level StateGraph so that it implements this control pattern:

```text
Observe current Case state
→ Deterministic Policy Supervisor
→ Select one required action OR use bounded LLM recommendation
→ Deterministic Action Authorisation
→ Execute approved tool
→ Verify result
→ Update authoritative state and dependencies
→ Re-evaluate:
   - continue;
   - selectively replan;
   - wait for external event;
   - interrupt for AIRO;
   - enter control exception;
   - cancel;
   - complete.
```

Target conceptual graph:

```mermaid
flowchart TD
    A["[STATE] Observe Triage Case"] --> B["[DET] Triage Policy Supervisor"]

    B -->|One required action| C["[DET] Select Required Action"]
    B -->|Several permitted evidence actions| D["[LLM] Bounded Evidence Action Recommender"]
    B -->|AIRO judgement required| H["[HITL] AIRO Governance Loop"]
    B -->|External information required| K["[EVENT] External Event Wait"]
    B -->|Cannot continue safely| L["[STATE] Control Exception"]
    B -->|Completion criteria met| M["[END] Case Completed"]

    C --> E["[DET] Authorise Selected Action"]
    D --> E

    E -->|Authorised| F["[TOOL] Execute Approved Triage Capability"]
    E -->|Human authority required| H
    E -->|Rejected or unsafe| L

    F --> G["[VERIFY] Verify Tool Result"]
    G --> I["[STATE] Update State and Evaluate Transition"]

    I -->|More permitted work| A
    I -->|Selective replanning| A
    I -->|AIRO judgement| H
    I -->|External wait| K
    I -->|Control failure| L
    I -->|Complete| M

    H --> N["[DET] Validate AIRO Decision"]
    N -->|Valid| A
    N -->|Invalid| H

    K --> O["[DET] Validate External Event"]
    O -->|Valid| A
    O -->|Continue waiting| K
```

The exact node structure may differ if the current repository already contains a better implementation, but the above control responsibilities must remain explicit and testable.

Do not merely rename the existing fixed nodes. The Coordinator must actually select actions from current Case State and policy.

# 4. Introduce a deterministic Triage Policy Supervisor

Implement or strengthen a deterministic Policy Supervisor.

The Supervisor must evaluate the full current Case State—not merely answer whether a numbered Gate should be skipped.

It must determine:

* allowed actions;
* prohibited actions;
* allowed tools;
* mandatory action, if exactly one action is required;
* whether the bounded LLM recommender may be called;
* whether AIRO judgement is required;
* which Human Governance Loop is required;
* whether an external event is required;
* expected event type;
* whether materiality and second-line engines are ready to run;
* whether external writing is permitted;
* remaining tool, retry, evidence-loop and total-loop budgets;
* effective Progressive Automation profile;
* whether completion criteria may be evaluated;
* whether the Case must enter a Control Exception.

Use a structured model similar to:

```python
class SupervisorDecision(BaseModel):
    policy_version: str

    allowed_actions: list[str]
    prohibited_actions: list[str]
    allowed_tools: list[str]

    mandatory_action: str | None
    llm_recommender_permitted: bool

```

The Policy Supervisor must be deterministic, versioned and independently testable. It must not call an LLM.

# 5. Add deterministic and bounded action selection

## Deterministic Action Selector

When there is one mandatory action, select it without calling an LLM.

Examples:

* questionnaire schema validation remains;
* no supporting evidence has been submitted;
* a mandatory evidence check remains;
* confirmed inputs are ready for deterministic engines;
* stale materiality must be recalculated;
* review pack is stale and must be regenerated;
* the Case must wait for an external response;
* final completion evaluation is required.

## Bounded LLM Evidence Action Recommender

Only call the LLM when:

* more than one permitted evidence-processing action is available;
* no deterministic priority rule resolves the choice;
* contextual reasoning is likely to add value.

Use structured output:

```python
class ActionProposal(BaseModel):
    selected_action: str
    selected_tool: str
    reason: str
    inputs_required: list[str]
    confidence: float
    human_review_recommended: bool
```

The LLM receives only:

* current Case objective;
* unresolved objectives;
* relevant Case context;
* allowed actions;
* allowed tools;
* previous verified results;
* execution budgets.

The LLM must not invent tools, actions or permissions.

The LLM must not select:

* materiality band;
* final second-line engagement;
* validation requirement;
* risk tier;
* automation profile;
* Gate bypass;
* final approval;
* override;
* formal publication.

If the LLM returns an unknown, prohibited or malformed action, reject it safely and either:

* use a deterministic fallback;
* retry within budget;
* or escalate to AIRO/Control Exception.

* an unknown tool is rejected;
* a mandatory action does not call the LLM;
* no safe action creates a Control Exception;
* budgets are enforced;
* automation profile cannot be increased by the LLM or Case user.

## Bounded Router

Test that:

* it is called only when multiple permitted actions exist;
* output must use the allowlist;
* malformed output uses safe fallback/escalation;
* it cannot choose materiality, second-line, profile, Gate bypass or publication;
* low-confidence recommendations are handled according to policy.

## Authorisation

Test that:

* deterministic and LLM-selected actions both require authorisation;
* stale-state actions are rejected;
* missing input blocks execution;
* external action requires explicit authority.

## Tool Registry

Test:

* input/output schemas;
* permission and authority classes;
* timeout and retry behaviour;
* idempotency;
* version capture.

## Result Verification

Test that:

* unsupported citations are rejected;
* prompt injection inside evidence is treated as untrusted content;
* unauthorised risk decisions are rejected;
* unverified results cannot update confirmed facts;
* failed results remain in execution history;
* stale tool output cannot become current.

## Replanning and invalidation

Test that:

* changed questionnaire facts invalidate only dependent outputs;
* new evidence triggers affected checks;
* unrelated verified results remain current;
* review pack cannot use stale results;
* material change invalidates an affected prior AIRO decision;
* previous and replacement results remain auditable.

## Human Governance

Test that:

* routine Cases do not enter meaningless evidence/exception Gates;
* material conflicts trigger the correct Governance Loop;
* final triage remains mandatory under Human-Governed and Conditional Review;
* publication approval remains mandatory for formal external writes;
* invalid human actions are rejected;
* rationale and authority requirements are enforced;
* duplicate decisions are idempotently rejected or ignored.

## External events

Test that:

* correct event resumes the correct Case;
* invalid correlation ID cannot resume;
* duplicate event is idempotent;
* stale event cannot overwrite current state;
* timeout invokes the configured escalation.

## Control Exception

Test:

* loop budget exhaustion;
* tool budget exhaustion;
* repeated verification failure;
* unknown state;
* safe recovery;
* authorised cancellation;
* no silent continuation after a control failure.

## Completion

Test that a Case cannot complete while:

* mandatory objectives remain;
* blocking gaps or conflicts remain;
* required human decisions are missing;
* current deterministic results are absent;
* review pack is stale;
* consequential actions are unreconciled.
