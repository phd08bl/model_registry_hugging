# Important boundary between Stage 2 and Stage 3

This should be explicit in the standard.

**Stage 2 asks:**

> **“Is this important enough to investigate, and where should we start?”**

**Stage 3 asks:**

> **“How does this process actually work, where exactly are the problems, and what should we take forward?”**

Therefore Stage 2 should **not** require:

detailed subprocess decomposition, root-cause analysis, validated baselines, detailed requirements, solution selection, Copilot-vs-Cortex decisions, PoC plans, or child-case creation.

Those come from Discovery.

The principle I would use for Stage 2 is:

> **Prioritise the outcome, establish accountability, choose the first discovery scope, and mobilise enough capacity to learn — without prematurely approving what to build.**

That gives you a strong transition from the lightweight **Stage 1 candidate intake** into the evidence-heavy **Stage 3 FDE Discovery**, while keeping Leadership's role appropriately focused on priorities, ownership and resources.

# Practical Delivery-Route Logic

The FDE should normally move from lower to higher complexity:

**Process change → Guidance / Template → Existing Capability → Copilot / Prompt → Workflow Automation → Analytical Tool / Service → Copilot Agent → Controlled MRO Backend / Cortex + Harness → Custom Application**

The principle is:

> **Additional technical complexity must be justified by a requirement that the simpler option cannot meet.**

For example:

| Requirement | Likely route |
|---|---|
| Human already knows what to do; AI mainly drafts/summarises | Copilot / controlled prompt |
| Workflow is predefined and mostly deterministic | Workflow automation |
| Specialist calculations or analytics are required | MRO analytical tool/service |
| Bounded conversational workflow with standard connectors | Copilot Agent |
| Need persistent state, specialist tools, controlled methodology, detailed traces/HITL or complex orchestration | Cortex + MRO Agent Harness |
| Existing enterprise/MRO capability already meets requirements | Reuse rather than build |

This is guidance, not an automatic scoring engine.

# Selecting the Appropriate Experiment Type

Stage 5 should not force every case through both a PoC and a Vertical Slice.

Use the experiment type that addresses the actual uncertainty.

| Experiment type | Use when | Main question |
|---|---|---|
| **Capability PoC** | The underlying technical/AI/analytical capability is uncertain | **Can the core capability work?** |
| **Vertical Slice** | Core capability is plausible/proven, but workflow, integration, evidence or controls are uncertain | **Can one realistic end-to-end path work?** |
| **User Trial** | Technology is relatively known, but usability/adoption/process fit is uncertain | **Can users successfully use this in the real process?** |
| **PoC + Vertical Slice** | Both the core capability and end-to-end workflow are materially uncertain | **Can it work, and can it work in the process?** |
| **Light validation only** | Solution is simple/proven and Stage 4 concluded a substantial experiment adds little value | **Does the proposed change behave as expected before delivery?** |

For example:

**Controlled Copilot prompt for report drafting**

may only need:

> representative user trial + quality testing.

A more complex:

**Independent Validation Agent**

may need:

> capability PoC → vertical slice → specialist evaluation.

# Baseline & Success Measures

Baseline should be used where it materially improves decision-making.

For example:

| Area | Baseline | Stage 5 result | Target / threshold |
|---|---:|---:|---:|
| Initial review effort | 4 hrs | 2.5 hrs | ≤3 hrs |
| Relevant issues identified | 80% manual benchmark | 88% | ≥85% |
| Unsupported findings | — | 6% | ≤10% |
| User completion | — | 5/5 users | ≥4/5 |

But do not create artificial numeric targets where quality is inherently qualitative.

Expert assessment may be appropriate for:

- usefulness;
- reasoning quality;
- appropriateness of recommendations;
- methodology adherence.

In those cases, define the evaluation rubric **before** the test.

---

# Controls and Human Gates

The experiment should represent the controls necessary to answer the experiment question.

For example:

- validator must approve an AI recommendation;
- agent cannot submit/change an official record;
- retrieved evidence must retain source reference;
- user identity must be logged;
- test data must remain within an authorised environment.

However, Stage 5 does not necessarily need every final production control fully implemented.

A useful distinction is:

### Controls needed to validate the experiment

Must be represented in Stage 5.

### Production controls

Can be identified as Stage 6 production-readiness requirements.

For example:

```text
Stage 5
Human approval simulated/enforced
        ↓
Evidence shows workflow works
        ↓
Stage 6
Define production RBAC, retention and audit implementation
```

# Failures Are Evidence

I would explicitly state this in the standard.

The experiment should capture:

- incorrect outputs;
- tool failures;
- retrieval misses;
- user confusion;
- latency;
- missing data;
- control failures;
- cases requiring unexpected human intervention.

Do not quietly fix the prototype and erase the original failure.

Failures often tell Stage 6 more about production requirements than successful test cases.

# Gate 5A — Core Capability Viability

Use Gate 5A where a capability PoC was required.

### Question

> **Has the core capability demonstrated enough value and feasibility to justify further progression?**

| Decision | Meaning |
|---|---|
| **Proceed** | Core capability sufficiently demonstrated |
| **Proceed with conditions** | Evidence positive but defined issues remain |
| **Iterate bounded experiment** | Small specific gap remains that can reasonably be tested |
| **Return to Stage 4** | Proposed solution/route should be reconsidered |
| **Stop** | Capability/value not sufficiently demonstrated |

Avoid endless PoC cycles.

If several iterations still cannot demonstrate the hypothesis, that is evidence in itself.

- integrations;
- user interaction;
- human gates;
- controls;
- evidence/traceability;
- exception/failure path.

**Proceed / Proceed with Conditions / Iterate / Return to Stage 4 / Stop**

# Stage 5 Operating Principle

> **Test the riskiest material uncertainty with the smallest credible experiment. Define success before testing, use representative cases, retain failures as evidence, and avoid turning a PoC into an uncontrolled early production build.**

A second useful standard is:

> **PoC proves the capability; Vertical Slice proves the workflow; Stage 7 production testing proves the product.**

And I would keep your exit authority principle, strengthened slightly:

> **Stage 5 produces evidence for a delivery decision but does not authorise production deployment. Successful Stage 5 cases move to Stage 6, where experiment findings, limitations and remaining gaps are converted into explicit production-readiness and control requirements.**


The most important improvement here is that Stage 5 is now directly driven by **Stage 4 evidence gaps**. That creates a clean chain: **Discovery identifies the problem → Stage 4 chooses the route and identifies uncertainty → Stage 5 produces evidence to resolve that uncertainty → Stage 6 decides what is required for controlled production.**


你的 Stage 6 设计需要把两件事合在一起，但要清楚区分：

1. **Evaluate what Stage 5 actually proved** — 是否达到预先定义的 acceptance criteria，失败、修正成本和limitations是什么。
2. **Translate that evidence into production-readiness requirements** — 如果继续，生产化还需要哪些 controls、ownership、monitoring、security/data/access、support 和 governance。

我不建议把 Stage 6 变成一个“大而全的 governance review”。更实用的是用四张核心 Cards：**Results Evaluation → Production Readiness → Ownership & Support → Gate Decision**。

# Risk-Based Governance

Stage 6 should avoid a one-size-fits-all governance checklist.

The FDE should first ask:

> **Which governance domains actually apply to this solution?**

Possible domains include:

- Process/control risk
- AI/model risk
- Data/privacy
- Information security
- Architecture
- Operational resilience
- Access management
- Records/evidence retention
- Change/release management

Then only applicable reviews appear.

For example:

### Controlled Copilot drafting prompt

May require relatively lightweight:

- approved data usage;
- human review;
- prompt/version ownership;
- usage guidance.

### Cortex + Agent Harness interacting with MRO systems

May require substantially more:

- identity;
- tool permissions;
- persistent state controls;
- logging;
- human approval gates;
- failure recovery;
- evaluation/regression framework;
- configuration/model versioning;
- production monitoring.

The Stage 6 process should therefore be **risk-proportionate**.

# Independent Challenge

I agree with your proposed addition and would make it explicit but proportionate.

Independent challenge should be expected where the solution is materially higher-impact because of factors such as:

- significant MRO decision support;
- autonomous/agentic actions;
- material methodology implementation;
- sensitive systems/data;
- significant control dependency;
- wide MRO reuse;
- substantial production investment.

The reviewer should challenge:

- whether Stage 5 evidence genuinely supports the conclusion;
- whether failed/conditional cases have been properly represented;
- whether controls are sufficient;
- whether proposed production requirements address known weaknesses;
- whether the delivery route remains proportionate.

A useful rule is:

> **The principal designer should not be the sole challenger of a material solution.**

If Sai facilitates/challenges a review, and Sai was the principal solution designer, another suitable reviewer should challenge the material conclusions.

# Adoption Review Questions

The review should explicitly ask:

- Are intended users using the capability?
- Are users bypassing it?
- Are they using only part of it?
- Has an unofficial workaround emerged?
- Are users correcting outputs more often than expected?
- Has the change reduced effort or simply transferred work to another team?
- Are required human controls still operating?
- Are support demands sustainable?
- Have business/process conditions changed since rollout?
- Are there groups for whom the capability works materially better or worse?

Low adoption is itself evidence.

The FDE team should determine whether the cause is:

- poor solution quality;
- poor process fit;
- training/communication;
- workflow friction;
- insufficient need;
- changed priorities;
- technical reliability;
- resistance caused by genuine process/control concerns.

# Review Timing

I agree with your principle that timing should be proportionate.

Do not impose exactly the same review cycle on every solution.

A useful default pattern could be:

### Early Operational Review

Several weeks after rollout.

Focus on:

- adoption;
- incidents;
- workflow issues;
- support burden;
- user corrections;
- immediate control issues.

### Benefits Review

Approximately **2–3 months after meaningful adoption**, where that is enough time for outcomes to become observable.

Focus on:

- baseline vs actual benefit;
- sustained adoption;
- quality/control outcomes;
- reuse;
- scaling;
- closure.

For some low-volume processes, a calendar-based three-month review may be meaningless.

Instead use:

> **after X representative cases / sufficient operating evidence**

where more appropriate.

# Gate 8 — Outcome, Scaling & Closure Decision

## Key Question

> **Has the solution created sufficient sustainable value, and what should MRO do next?**

Possible decisions:

| Decision | Meaning |
|---|---|
| **Close — Benefits Realised** | Intended outcome materially achieved; normal BAU ownership continues |
| **Close — Partial Benefits Accepted** | Some value realised; remaining limitations accepted |
| **Continue Benefits Monitoring** | Not yet enough operating evidence for final conclusion |
| **Improve through BAU Backlog** | Solution remains valid but incremental changes are required |

| **Scale** | Expand the proven solution to wider users/process scope |

# Stage 8 Operating Principles

### 1. Deployment is not a benefit

> **A tool being live is not evidence that the original process problem has improved.**

Benefits must reconnect to the original outcome.

### 2. Adoption is evidence

If users do not use the solution, understand why rather than simply reporting “deployment complete”.

### 3. Measure net effort

Include human review, corrections, support and new work created by the solution.

### 4. Reuse should be evidence-led

> **Do not turn every successful case into a shared platform capability.**

Reuse should be supported by common need, evidence and sustainable ownership.

### 5. FDE closure does not remove BAU ownership

Closing the FDE case means the improvement lifecycle has reached an appropriate conclusion. Product/service/process ownership continues.

### 6. Learning should compound across waves

Stage 8 evidence from one process variant should reduce discovery and delivery effort for later variants.

# Stage 8 Standard

> **Stage 8 determines whether the delivered change is used, produces the intended sustainable process outcome, remains operationally proportionate, and creates learning or reusable capability that can improve future MRO work. The stage formally closes or redirects the FDE case while preserving clear BAU ownership.**

# Proportionate Use of the FDE Toolkit

I strongly agree with retaining this principle.

| Route | Expected use |
|---|---|
| **Light** | Candidate/priority record; only relevant Discovery/Route fields; simple testing/acceptance; short handover and benefits conclusion |
| **Standard** | Relevant cards across all stages; structured Discovery; option assessment; bounded experiment; evaluation; delivery evidence; benefits review |
| **Enhanced** | Full evidence trail; architecture/data/control assessment; formal methodology/version controls; independent challenge; vertical slice; detailed production testing; controlled rollout; richer monitoring |

Importantly:

> **Light / Standard / Enhanced determines depth, not whether the eight-stage logic exists.**

Even a Light case should still answer:

**Problem → Priority → Understand → Choose → Prove → Assess → Deliver → Measure**

It simply does so with much less documentation.

# Overall FDE Discipline

The line from your proposal is worth retaining almost exactly:

> **Use Cards to structure the questions, Activities to guide the FDE work, Evidence to verify conclusions, Checklists to challenge readiness, Gates to make decisions, and Generated Artefacts to communicate the record.**

I would add one final clause:

> **Use proportionality to determine how much of each is required.**

That captures the central philosophy of the whole eight-stage model: structured enough to make MRO decisions evidence-led and reproducible, but not so heavy that FDE becomes a documentation or governance exercise.
